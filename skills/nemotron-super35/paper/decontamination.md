# §3.12 Benchmark Decontamination (report p.29)

Post-training data from many synthetic and curated sources can absorb benchmark content as verbatim copies, paraphrases, translations, augmentations, and other derived samples that string matching misses. Contamination inflates scores and, because the same benchmarks guide training monitoring and checkpoint selection, "it can also result in a worse final model." NVIDIA checked **post-training data** against **30 benchmarks** (Appendix D.2) and removed samples related to benchmark questions. This **data-side** detection complements **model-side** detection with CoDeC (Zawalski et al., 2026), which probes a trained model for traces of a benchmark. **"The pipeline will be released as part of NeMo Curator."**

Whether pretraining, mid-training, or Lightning's data were decontaminated this way is not reported. (Separately, §2.5 says every mid-training source was decontaminated against SWE-bench and Terminal-Bench, method not described.)

## Pipeline (four stages, every training sample)

1. **Normalization.** Reduce the sample to its problem statement (where leakage could occur); strip text templates that recur across its dataset to avoid spurious matches.
2. **Candidate retrieval.** Compare with every benchmark question using two signals:
   - *Verbatim overlap*: fraction of the question's n-grams found in the sample. Catches copies even inside longer texts; misses rephrasing.
   - *Semantic overlap*: embedding similarity between parts of the two texts. Catches paraphrases; can be biased by style similarity.
   Both shortlist the likeliest candidates (high recall).
3. **Verification.** An LLM judge classifies each shortlisted (sample, question) pair as contamination (direct copy, paraphrase, answer leakage, method leakage) or benign (style overlap, no contamination) and rates severity. The shortlist is small, so a strong judge is affordable.
4. **Removal.** Remove a sample if the judge finds it severely contaminated with respect to any benchmark question.

## Results (§3.12)

| Quantity | Value |
|---|---|
| Samples removed | 20,671 (~0.09% of post-training data) |
| - SFT | 14,793 |
| - RL | 5,878 |
| Benchmark questions matched | 1,808 (6.0% of all benchmark questions) |
| Benchmarks with any match | 22 of 30 |
| Candidate pairs judged "severe" | ~3% |

Derived, not reported: 14,793 + 5,878 = 20,671 (consistent); 0.09% implies roughly 23M post-training samples in total; 6.0% implies roughly 30K benchmark questions in total. Exact totals are not reported.

# Appendix D Details (report pp.69-73)

## D.1 Configuration (Table 36)

Benchmark side (question store, n-gram index, embedding index) is built once and shared by all runs. Training data processed in shards on CPU nodes; embeddings and judge decisions served by remote endpoints.

| Component | Setting |
|---|---|
| Scored text | user turn (SFT) or prompt (RL), dataset-level boilerplate removed |
| Verbatim overlap | word 8- and 13-grams; shared n-grams / n-grams of the benchmark question |
| Embedding model | Qwen3-Embedding-0.6B |
| Chunking | 512-byte windows, 256-byte stride (sample and question) |
| Semantic overlap | maximum cosine similarity over chunk pairs |
| Candidate selection | per question: top 20 by combined score + top 2 per signal |
| Judge gate | semantic overlap >= 0.75 or verbatim overlap >= 0.5 |
| Judge model | Claude Opus 4.6, temperature 0 |
| Judge input | each text capped at 8,000 characters (head and tail kept) |
| Removal rule | contaminating label (Table 37) with severity >= 3 |

How the "combined score" weights the two signals is not reported. Only the user turn / prompt is scored, not responses (see D.6).

## D.2 Benchmarks checked (30)

MATH-500, IFBench, KernelBench, MMLU-Pro, Terminal-Bench 2.0, Terminal-Bench 2.1, NV Chat Benchmark, Humanity's Last Exam, GPQA Diamond, CBRN, BBQ, TIR-Bench, SciCode, AA-Omniscience, AA-LCR, ICPC-Eval, PinchBench, ClawEval, SWE-bench Pro, SWE-bench Verified, MRCR, Tau-Bench, BrowseComp, CritPt, GDPval, IOI, MCP-Atlas, ProfBench, SWE-Atlas-QnA, SWE-bench Multilingual.

Selection spans established and modern benchmarks, with CoDeC contamination evaluations as additional guidance.

Matches concentrate in a few benchmarks:
- **MATH-500:** about a quarter of problems matched.
- **IFBench, KernelBench:** about 15% of items each.
- **MMLU-Pro:** largest absolute count, **1,254** matched questions (~69% of the 1,808 total; derived).
- **Eight benchmarks** — "mostly recent agentic and expert-level ones" — had no matches. Which eight is not reported.

Per-benchmark counts beyond these are not reported.

## D.3 Judge prompt and labels (Table 37)

User message: a JSON object `{"training_sample": ..., "benchmark_question": ...}` followed by "Return only the JSON object." JSON escaping keeps boundaries unambiguous when samples contain code, markup, or instructions. The system prompt asks whether having the training sample in the data "would give an unfair advantage on the benchmark question", to pick the single best label (listed roughly strongest-first), then rate integers 0-4:
- **severity**: degree of unfair advantage, 0 (harmless to keep) to 4 (must be removed);
- **confidence**: confidence in the severity rating, 0 (unsure) to 4 (certain).

Output: `{"reasoning": "<one concise sentence>", "label": "...", "severity": <0-4>, "confidence": <0-4>}` with reasoning first.

| Label | Contaminating | Definition given to the judge |
|---|---|---|
| direct_copy | yes | reproduces the benchmark question (and/or its answer) verbatim or with only minor edits |
| paraphrase | yes | restates the same specific problem, with wording or irrelevant details changed |
| answer_leakage | yes | solving the training problem yields the benchmark's answer (special case, sub-problem, or key step) |
| method_leakage | yes | benchmark solved by the same method, differing only in surface details or numeric values |
| style_overlap | no | shares only topic, domain, or format: general knowledge, not the specific problem |
| no_contamination | no | unrelated; similarity coincidental |

A sample is removed if any of its pairs has a contaminating label with severity >= 3. The confidence score is not used in the removal rule as stated.

## D.4 Synthetic evaluation

No ground-truth labels exist for real data, so all questions of a target benchmark are transformed with **13 augmentations** at **four strengths (0.25, 0.5, 0.75, 0.9)**:
- **Surface:** verbatim copy, character noise, case flipping, whitespace insertion.
- **Structural:** crop to beginning / middle / end, word dropout, local word reordering, burial among other questions.
- **Semantic (another LLM):** paraphrase (light rewording to full restyle), translation (increasingly distant languages), abstraction (progressive generalization).

Every transformed question is a positive. Negatives are unmodified questions from a hard-to-distinguish same-domain benchmark. The augmenting LLM differs from the judge, so the judge cannot recognize its own rewrites (the augmenting model is not named).

| Target | Positives | Negatives (source) |
|---|---|---|
| Terminal-Bench 2.1 | 4,361 | 731 (SWE-bench Pro) |
| GPQA Diamond | 9,702 | 12,032 (MMLU-Pro) |

**Table 38 — each signal alone, at thresholds that flag no negatives**

| Signal (alone) | TB2.1 recall % | TB2.1 false pos. | GPQA recall % | GPQA false pos. |
|---|---|---|---|---|
| Verbatim overlap >= 0.5 | 26.3 | 0 / 731 | 25.7 | 0 / 12,032 |
| Semantic overlap >= 0.85 | 61.2 | 0 / 731 | 47.4 | 0 / 12,032 |
| LLM judge (severity >= 3) | 87.5 | 0 / 731 | 79.1 | 1 / 12,032 |

The judge recovers most positives with a single false positive in 12,763 negatives. Verbatim catches about a quarter (copies and mild surface edits), semantic about half. GPQA recall is lower because its short multiple-choice questions carry less distinctive text than Terminal-Bench's long task descriptions. Note: the semantic threshold here (0.85) is the standalone-signal threshold; the production judge gate uses 0.75 (Table 36).

**Table 39 — recall by augmentation, averaged over strengths, union of the three signals** (a positive counts only if matched to its own source question)

| Augmentation | Terminal-Bench 2.1 % | GPQA Diamond % |
|---|---|---|
| Verbatim copy | 100.0 | 100.0 |
| Case flipping | 100.0 | 100.0 |
| Burial among other questions | 100.0 | 100.0 |
| Local word reordering | 99.7 | 99.4 |
| LLM paraphrase | 97.2 | 93.2 |
| LLM translation | 94.7 | 79.4 |
| Whitespace noise | 92.7 | 93.9 |
| Crop to beginning | 90.2 | 68.8 |
| Character noise | 88.5 | 84.8 |
| Crop to middle | 82.6 | 63.1 |
| Crop to end | 80.9 | 71.1 |
| LLM abstraction | 73.6 | 65.0 |
| Word dropout | 67.1 | 55.3 |

Translations are recovered almost entirely through the judge. Misses concentrate in aggressive crops, heavy word dropout, and strong abstraction at the highest strengths, where the text often no longer identifies the source. Because every transform counts as a positive however far it drifted, these recalls are conservative (report claim). Per-strength breakdowns are not reported.

## D.5 Notable cases (no benchmark items reproduced)

- **Translated and reformulated problems:** several MATH-500 problems appear translated into Chinese, some reformulated to ask for a derived quantity (e.g., sum of numerator and denominator of the answer fraction); almost no shared n-grams, yet they teach the answer.
- **Cross-lingual chat prompts:** benchmark prompts reappear in RLHF prompt collections in Chinese, Japanese, Spanish, Polish, Russian, German, French, sometimes with changed numbers (a short-distance travel puzzle posed with 50 instead of 500 meters).
- **Benchmark tasks inside agentic data:** Terminal-Bench task descriptions nearly verbatim inside agentic RL prompts, prefixed with environment-setup instructions and different file paths.
- **Expert-level questions:** HLE questions in math and tool-integrated-reasoning data as copies, paraphrases, or problems whose solution contains the benchmark answer as an intermediate step.

"All those cases were prevented from entering the training mix."

## D.6 Limitations (as stated)

- **Recall bounded by candidate selection:** the judge only rules on pairs selected by the cheap signals; a contaminated sample outside a question's top candidates or below the similarity gate is always kept.
- **Only the problem statement is scored:** contamination via the same answer set or other artifacts is not detected.
- **The evaluation is a proxy:** augmentations approximate, but do not exhaust, real contamination.

# Contradictions and inconsistencies in the source
- §3.12 says "over 10,000 variants of Terminal-Bench 2.1 and GPQA Diamond questions" mixed "with a similar number of same-domain distractors". D.4 gives 14,063 positives (4,361 + 9,702) and 12,763 negatives (731 + 12,032): consistent in aggregate, but per benchmark Terminal-Bench 2.1 has ~6x more positives than negatives (4,361 vs 731).
- §3.12 attributes the 87.5% / 79.1% to "the judge correctly identified"; Table 38 shows these are the judge's standalone recall, while Table 39 reports union-of-signals recall per augmentation. Both are consistent but measure different things.
- No numeric inconsistencies found: 14,793 + 5,878 = 20,671; 30 - 8 = 22 benchmarks with matches; the D.2 list has exactly 30 entries; Table 39 has exactly 13 augmentations.

# Caveats
- Applies to post-training (SFT and RL) data for Super; coverage of pretraining, vision data, and Lightning is not reported. Mid-training data was decontaminated against SWE-bench and Terminal-Bench only (§2.5), with no method given.
- The pipeline is announced for NeMo Curator; the report gives no release date or link.
- Synthetic recall is measured on two benchmarks only (Terminal-Bench 2.1, GPQA Diamond).
